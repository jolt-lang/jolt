# Jolt 0.8.26, JVM Clojure and Babashka by workload category

November 10, 2026 · Seed `42` · 47 projects · 564 fresh processes · All 7,332 executions, including warmups, matched both the oracle and the Jolt 0.8.24 sweep.

**Jolt’s clearest change was repeat startup/load.** With the project cache populated, 0.8.26 loaded faster than 0.8.24 on 28 of 37 individual categories. The median per-category reduction was 5.9%. Warm execution was close across versions, with a median reduction of 0.6%.

## Changes across the 37 individual categories

Each cell gives the median percentage change in elapsed time across the 37 matched category pairs. Negative values mean less time. JVM Clojure and Babashka used the same versions in both sweeps and were measured again. Their changes show the run-to-run variation on this host.

| --- | ---: | ---: | ---: |
| Jolt | +3.6% | −5.9% | −0.6% |
| JVM Clojure | +4.7% | +2.0% | −3.8% |
| Babashka | +5.0% | −1.4% | −0.8% |

- **Startup/load.** Babashka had the shortest first load and the lowest median repeat load on all 37 individual categories. Jolt loaded faster than JVM Clojure on two individual categories on first launch and on all 37 on repeat launches. The median repeat-load time across categories was 233 ms for Jolt, 901 ms for JVM Clojure and 68 ms for Babashka.
- **Execution.** Jolt had a lower execution median than Babashka on 28 of 37 categories and than JVM Clojure on 13. JVM Clojure had the lowest time of the three on 23 categories, Jolt on 13 and Babashka on one (`core/text`). Jolt led both on protocols at 52.2 ms, while JVM Clojure led on multimethods at 6.8 ms.
- **Filesystem paths.** The combined `babashka/fs` profile took 1,188 ms on Jolt, up 2.2% from 1,162 ms. JVM Clojure took 78 ms and Babashka took 221 ms in this sweep. Across the five individual path operations, Jolt used 12.7–16.3× the JVM time and 5.4–5.9× the Babashka time. Each measurement includes building paths in memory and folding the returned text into the checksum.
- **Largest Jolt execution changes.** `jvm/math/min` took 7.8% less time (32.6 to 30.1 ms), and `jvm/atomic-long/add-and-get` took 6.1% less (138.8 to 130.4 ms). `babashka/fs/strip-ext` had the largest increase at 4.7% (1,207 to 1,264 ms).

## Measurement conditions

- **Host and versions.** Apple M3 Ultra virtual machine, 24 logical CPUs, 32 GiB RAM, macOS 15.7.3 arm64. Installed Homebrew Jolt 0.8.26, JVM Clojure 1.12.4 (CLI 1.12.4.1618, OpenJDK 25.0.2), and Babashka 1.12.218. Generator and runner at `ef51da36`.
- **Workloads.** Seed `42`, target 5,000 nonblank lines, namespace target 400 lines, runtime input `42`, 100 passes per execution. One directory per profile. All 808 generated Clojure source files, the 47 models and manifests, the oracles and the measurement scripts matched the previous run byte for byte. All three runtimes loaded the same project for a given row. The sweep covered all 37 leaves, eight distinct multi-leaf parent selections and two controls. The mixed workload selected 20 of the 26 available Java and filesystem operations. The individual runs exercised all 26. A parent with a single leaf produces the same program as that leaf. `all` enables every category. `baseline` disables every optional category and still executes the generated workers and checksum fold.
- **Startup/load.** Wall time from process launch through the readiness marker after loading the project. Before measurement, the JVM CLI prepared each project's classpath and dependencies with `-P`, including `babashka/fs` 0.3.17 where selected. Each project's first launch used its own empty Jolt AOT cache directory. Three subsequent fresh launches reused that directory. Repeat-load figures use the median of those three later launches. The OS page cache stayed enabled throughout. “First” means first launch against that project cache.
- **Execution.** Each later process ran 10 warmups and 7 timed executions. The execution columns give the median of the three process medians, in milliseconds per 100 passes. Timing covers only `workload.main/run`. Every warmup and sample restarted from the same input and was compared with the independent oracle. JVM tiered compilation and GC can continue during sampling.
- **Ordering.** The sweep ran one benchmark at a time. Within a profile, the stock runner always launched Jolt, JVM Clojure, then Babashka. Each of the four rounds used the same shuffled profile order as its counterpart in the previous sweep. Startup omits dependency downloads, and execution omits launch, loading, oracle computation and I/O with the runner.
- **Reading the rows.** The size target controls source lines. It allows the amount of executed work to change across selectors. “Kernels/pass” counts generated kernel invocations from worker folds per pass. Those kernels can do very different work, including helpers, allocations, conversions and checksum arithmetic. Compare runtimes within a row. For example, the baseline invokes 3,960 small kernels per pass while the mixed workload invokes 34. The `load/unused` row includes generated orphan source outside the entry point’s require graph. The filesystem rows build paths and fold their returned text into the checksum in memory.

## Reproduce one row

From the repository root, the following reproduces the `babashka/fs` profile. Use an empty project directory. Substitute a table selector after `--only` for another row. For `all`, omit `--only`. For `baseline`, use `--exclude babashka,core,dispatch,jvm,load,syntax`.

```sh
kit="$PWD/benchmarks/generated-project"
project="$kit/out/reproduce-fs-seed42-0.8.26"
bb "$kit/generate.bb" "$project" --seed 42 --lines 5k --namespace-lines 400 --only babashka/fs
(
  cd "$project" || exit 1
  if rg -q ':bench-jvm' deps.edn; then
    clojure -Srepro -P -M:bench-jvm
  else
    clojure -Srepro -P -M
  fi
  export JOLT_CACHE_DIR="$PWD/aot-cache"
  bb run.bb . 42 100 --warmup 0 --samples 1
  for round in 1 2 3; do
    bb run.bb . 42 100 --warmup 10 --samples 7
  done
)
```

The CSV records one row per fresh process. Launch 0 is the first project load and first execution. Launches 1–3 each contain a startup/load observation and seven execution observations in time order. All times are milliseconds. [Per-process measurements](2026-11-10-seed42-samples.csv)
